# Специфікація: економія LLM-викликів (проксі myllm + docgen-пайплайн)

Статус: чернетка для обговорення
Дата: 2026-07-04
Джерела даних: `nitra/cursor/.n-cursor/llm-trace.jsonl` (3506 викликів, 11–26.06.2026),
`~/.omlx/stats.json`, `~/.omlx/settings.json`, код `app/src-tauri/src/omlx/`.

## 1. Контекст і виміряні факти

Локальний inference-стек: клієнти → myllm-проксі (`proxy.rs`) → oMLX (`:8000`,
`max_concurrent_requests: 1`). Основний споживач — docgen-пайплайн
(`nitra/cursor/npm/rules/doc-files/`), 5 одноразових викликів на файл:
behavior → api → overview → critic → refine.

Виміряно на вікні 11–26 червня:

| Метрика | Значення |
|---|---|
| Викликів у трейсі | 3506 (96% ok) |
| Prompt / completion токенів | 2.98M / 543k |
| Сумарний wall-time | ~9.8 год (сер. 10 с/виклик) |
| Prefill vs decode на сервері (gemma-4-e4b, весь час) | 15 600 с vs 142 750 с → **~90% часу — декодування** |
| Префікс-кеш oMLX (уже ввімкнений, SSD 16GB) | 29.3M з 47.5M prompt-токенів з кешу (62%) |
| **Точні дублікати запитів** | **943 виклики (26.9%) = 94.6 хв + 484k токенів дарма** |
| Дублікати в межах 10 хв (retry/цикли) | 116 з 195 груп |
| Критик повернув `NONE` | **0 з 650** → refine виконується завжди (critic+refine = 37% трафіку) |
| Відмови prefill memory guard | 107 (корінь знайдено на клієнті — див. напрям F; `compress.rs` лікує лише multi-message сесії) |
| Швидкість декодування | ~19 tok/s median |
| Hot cache (RAM) | вимкнений (`hot_cache_max_size: 0`) |

Висновки, що задають напрям:

1. Префікс-кеш уже працює — перестановка промптів чи «одна сесія» дає мало.
2. Найдешевший великий виграш — не рахувати те, що вже рахували (дублікати).
3. Другий важіль — не робити зайвих кроків (critic/refine без зупинки).
4. По латентності головне — декодування, не prefill.

## 2. Цілі

- Зрізати ≥25% викликів без зміни якості виходу (дублікати + зайві refine).
- Зробити повторні прогони docgen детермінованими (кеш замість resample при temp 0.2).
- Прискорити декодування без заміни моделі.
- Зробити ефект видимим: метрики кешу і розподілу часу в UI myllm.

## 3. Не-цілі

- Multi-turn «сесія» для docgen — відхилено: префікс-кеш сервера вже дає 62%
  хітів, накопичення контексту роздуває prefill і ризикує crossover фактів
  між файлами.
- Заміна моделі чи переписування docgen-промптів по суті (стиль, критерії).
- Семантичний (нечіткий) кеш відповідей — тільки exact-match.

## 4. Напрям A — response-кеш у проксі myllm

Місце: `app/src-tauri/src/omlx/` (новий `respcache.rs`, виклик з `proxy_handler`).

Дизайн:

- Ключ: `sha256(model + канонізовані messages + temperature + max_tokens +
  top_p + response_format + tools)`. Канонізація — після `compress_request_body`,
  щоб компресія не ламала ключ.
- Кешувати лише `POST /v1/chat/completions` зі статусом 200 і `stream: false`
  або повністю зібраний SSE (проксі вже накопичує копію байтів у `captured`).
- Сховище: JSONL/sled у app data dir; ліміт розміру (напр. 256MB) + TTL
  (напр. 7 діб), LRU-евікція.
- Політика вмикання: opt-in заголовком `x-myllm-cache: allow` АБО allowlist
  клієнтів у налаштуваннях (проксі вже резолвить процес-клієнт через
  `client_info`) — щоб інтерактивні чати не отримували консервовані відповіді.
- Відповідь з кешу віддається в тому ж форматі, що просив клієнт (JSON або
  реконструйований SSE), з заголовком `x-myllm-cache: hit`.
- У `RequestLogEntry` — нове поле `cache_hit: bool`.

Приймальні критерії:

- Повторний однаковий запит з увімкненим кешем не досягає upstream і
  повертається <50 мс.
- Помилки (4xx/5xx, guard-відмови) ніколи не кешуються.
- Історія запитів показує hit/miss; `proxy_clear_history` не чистить кеш,
  окрема команда `respcache_clear`.
- Очікуваний ефект на профілі docgen: −27% викликів, ~−95 хв на два тижні.

## 5. Напрям B — калібрування critic/refine (репо nitra/cursor)

Місце: `npm/rules/doc-files/docgen-prompts/main.mjs` (`criticMessages`) і код
пайплайна, що вирішує запуск refine.

Проблема: критик за 650 викликів жодного разу не повернув `NONE` — refine
безумовний, це ~37% усього трафіку.

Дизайн (кандидати, обрати після експерименту):

- Пере-промпт критика: явний дозвіл і приклад «чиста чернетка → NONE»;
  вимога вказувати цитату-доказ для кожного issue (без цитати issue
  відкидається парсером).
- Severity-гейт: критик маркує issues `major|minor`; refine запускається
  лише за наявності `major`.
- Механічний пре-фільтр перед критиком: заборонені generic-фрази, `##` у
  секції, наявність анкорів — перевіряються regex'ом; критик викликається
  лише коли механіка щось не покриває.

Приймальні критерії:

- На еталонному наборі (~30 файлів) частка пропущених refine ≥30% без
  падіння судді якості (`judge score` у фронтматері docs не гіршає).
- A/B: старий цикл vs новий на одному наборі, порівняння score і часу.

## 6. Напрям C — дедуплікація в пайплайні (репо nitra/cursor)

- In-run мемоізація: кеш `hash(messages) → content` на час одного прогону
  (116 груп дублікатів укладаються в 10 хв — це ретраї/цикли конвергенції).
- Content-hash gating між прогонами: docs-фронтматер уже містить `crc` —
  пропускати файли, чий `crc` не змінився, ще до формування промптів.
- Логувати в trace причину пропуску (`skipped: unchanged`), щоб економія
  була видима.

Приймальний критерій: повторний прогін docgen по незміненому репо робить
0 LLM-викликів.

## 7. Напрям D — швидкість декодування oMLX

Декодування — 90% часу, ~19 tok/s. Кроки дослідження (конфіг, без коду):

1. Увімкнути RAM hot cache (`hot_cache_max_size: 4GB`+) — зараз кеш
   тільки на SSD; заміряти prefill до/після.
2. Прогнати `burst_decode_mode`: `balanced` (поточний) vs альтернативи.
3. З'ясувати підтримку speculative/n-gram decoding в oMLX 0.4.x. Для
   refine-кроку (вихід ≈ переписаний вхід) n-gram acceptance був би високий.
4. Бенчмарк `mlx_lm.benchmark` для e4b на цій машині як базова лінія.

Приймальний критерій: рішення «прийняти/відхилити» для кожного пункту з
цифрами до/після; ціль — ≥25% приросту tok/s хоча б від одного заходу.

## 8. Напрям E — метрики в UI myllm

Місце: `app/src/` (вікно історії запитів) + агрегація в Rust.

- Панель зверху історії: response-cache hit rate, кількість дублікатів за
  вікно, розподіл prefill/decode (з `usage` + таймінгів), відмови guard,
  частка `prompt_compressed`.
- Джерело: `requests.jsonl` (уже пишеться) + нові поля з напряму A.
- Push-оновлення через існуючий event `omlx-request-logged`.

## 8а. Напрям F — гігієна промптів на клієнті (репо nitra/7n-test)

Повна спека: `nitra/7n-test/docs/specs/2026-07-04-omlx-prompt-budget.md`
(клієнтська половина цього ж вектора). Стислий зміст:

- **Першопричина найбільших промптів (124–177k символів) і серії
  guard-відмов** — необмежений runtime-probe вихід у gen-tests:
  `runtime-probe.mjs:112` серіалізує результат виклику export'а без
  ліміту, і `readSurvived("")` затягнув у промпт весь COVERAGE.md
  проєкту. Це пояснює, чому `compress.rs` (проксі) не рятував: запити
  gen-tests — 2-message one-shot, обидва повідомлення protected.
- **Фаза 1**: кап probe-виходу (600 символів, shape-summary замість
  значення при перевищенні) + запуск probe-сабпроцесу з tmp-cwd
  (детермінізм, без випадкового читання файлів проєкту) + обмежений
  backoff-retry на memory-guard у `pi-client.mjs` (15/30/60 с,
  одно-слотова черга oMLX вивільняє пам'ять сама) + структуровані поля
  `omlxCode`/`estimatedBytes`/`limitBytes` з тіла 400.
- **Фаза 2**: спільний `prompt-budget.mjs` (бюджет символів на
  промпт, батчинг fix-tests, per-call `maxTokens` за типом задачі).

Синергія з напрямами цієї спеки:

- Детермінований probe-вихід → байт-стабільні повторні промпти →
  вищий hit-rate префікс-кешу oMLX і майбутнього response-кешу (A).
- Response-кеш (A) зберігає лише 200-ки — не конфліктує з
  backoff-повтором ідентичного промпту після 400.
- Per-call `maxTokens` (фаза 2) сегментує ключ кешу A (ключ включає
  `max_tokens`) — врахувати при звірці hit-rate.
- Метрики E можуть показувати розмір промпту per-client — після
  фази 1 напряму F профіль 7n-test має впасти зі 124–177k до <40k.

## 10. Ризики

- **Кеш ховає недетермінізм як фічу**: при temp>0 кешована відповідь — одна
  з можливих; для docgen це бажано, для чатів — ні. Мітигація: opt-in.
- **Ключ кешу і compress.rs**: компресія змінює тіло; ключ рахувати після
  компресії, інакше однакові запити з різним pretty-print промахуються.
- **Критик-NONE може маскувати реальні дефекти**: тому A/B з суддею, а не
  сліпе ввімкнення.
- **`ssd_cache_max_size` в oMLX діє per-model, не глобально на директорію.**
  Перевірено кодом (`paged_ssd_cache.py:_scan_existing_files`/
  `_is_compatible_block` в `oMLX.app`) і логами `server.log`: скан при
  старті індексує й обмежує лише блоки поточної завантаженої моделі; блоки
  інших моделей — навмисно "skipped_incompatible", лишаються на диску без
  ліміту (щоб скан однієї моделі не видаляв кеш іншої). За 3 тижні логів
  проіндексований розмір стабільно 16.00 GB (ліміт дотримано), але
  `skipped_incompatible=21.14 GB` (кеш ≥5 інших колись завантажених
  моделей) — разом точно 37G з `du`. Тобто ефективна стеля директорії —
  `16GB × кількість колись завантажених моделей`, без крос-модельної
  евікції. Не блокер для напряму A/E, але варто зафіксувати як окремий
  пункт у напрямі D: або періодичне ручне прибирання
  (`omlx cache clear --model <name>`, якщо є), або запит на глобальний
  cap/крос-модельний GC в oMLX.

## 11. Відкриті питання

- Формат сховища кешу: JSONL-файл (просто, як requests.jsonl) чи sled/sqlite?
- Чи вмикати кеш за замовчуванням для CLI-клієнтів (`caller`-фільтр) і лише
  opt-in для чатів — або скрізь opt-in?
- Чи потрібен `seed` у запитах docgen (oMLX підтримує?) як альтернатива
  детермінізму через кеш.
